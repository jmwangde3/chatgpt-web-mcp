# 2026-11-19 Stability and Recovery Notes

## Scope

This maintenance patch fixes deterministic lifecycle and recovery defects reported during the cg-tray hover task. It does not claim to repair host-side tool injection, safe-delete policy, Windows ACL policy or non-interactive desktop limitations.

## 1. Browser process vs. Playwright connection

The MCP connects to its dedicated Chrome with `chromium.connectOverCDP()`. This is not the same client connection mode as `chromium.connect()`. In the pinned Playwright 1.62.1 implementation, a `connectOverCDP()` Browser is created with `_shouldCloseConnectionOnClose === false`. Its public `browser.close()` call reaches the Playwright server-side Chromium Browser dispatcher; the server closes the CDP WebSocket transport with `chromeTransport.closeAndWait()` and does not send a browser-shutdown command to Chrome.

The patch uses `disconnectCDPConnection()`:
- verify the Browser object exposes the expected `connectOverCDP` mode flag and that it is `false`;
- do not mutate `_shouldCloseConnectionOnClose`;
- call the public `browser.close()` API so the server-side CDP transport and artifacts are cleaned up;
- fail closed if the expected Playwright contract is missing or the flag indicates the different `connect()` mode;
- leave actual browser termination exclusively to the explicit, identity-verified `terminate()` path.

Do not set `_shouldCloseConnectionOnClose = true` on a `connectOverCDP()` Browser. That flag is used by Playwright's separate `connect()` client transport path; forcing it bypasses the server-side `connectOverCDP` cleanup and can leave `browser.close()` waiting for a disconnect event that never arrives.

The repository lockfile pins Playwright 1.62.1 and the helper checks the mode flag at runtime. Run:
```powershell
npm test
npm run verify:cdp-disconnect
```
The second command launches the configured Chrome with a temporary profile, attaches, creates a marker page, disconnects, reconnects and verifies that the same page remains and the CDP endpoint is still available. This is a real local browser test, not a provider login test.

## 2. Missing ChatGPT message identity

`LEGACY_IDENTITY_UNVERIFIED` means the task journal did not persist a stable per-message ID for the newly submitted user turn. It does not mean a Windows SID, OS user name or generic stable identity setting is missing. Do not fabricate a message ID from PID, URL, timestamp or prompt hash.

For an explicitly confirmed `abandon --confirm`, the patch adds one safe exit:
- if the original page URL is unchanged;
- user and assistant message counts exactly match the saved baseline;
- baseline prompt hash and available baseline message IDs match;
- the identity snapshot is valid;
- the page is idle;
- any active generation record belongs to this same task and its owner process is confirmed exited;

then the server can clear only that task's stale tracking. If the prompt appears, counts/IDs differ, the page is busy, or generation ownership is unknown, the task remains reserved. No send is retried.

For an unconfirmed send, inspect the original dedicated ChatGPT MCP browser/profile, not the ask-bridge browser. If the exact baseline is unchanged and idle, the user may explicitly run:
```powershell
node src/cli.js abandon <task_id> --confirm
```
This baseline-abandon recovery path is ChatGPT-specific. Gemini `SEND_UNCONFIRMED` retains its provider-specific `inspect_page` recovery and must not be routed through ChatGPT's stable-message-ID checks.

If the prompt is visible, do not abandon; continue recovery with the original task and conversation.

## 3. Stale locks

`node src/cli.js doctor` remains read-only. The new explicit:
```powershell
node src/cli.js doctor --repair
```
attempts to acquire/release only lock files whose owner is independently classified DEAD or PID_REUSED. The normal crash-recoverable `acquireLock()` protocol performs reclamation. LIVE and UNKNOWN owners are preserved. Path/profile security checks run before mutation.

This command:
- does not delete lock files by broad wildcard;
- does not edit `tasks.json`;
- does not archive or clear uncertain tasks;
- does not release task reservations;
- does not repair unsafe ACLs.

The reported 34 active / 30 uncertain tasks must be reviewed by state and original page evidence. Do not batch-archive them to make the counter smaller.

## 4. Host-side issues that source code cannot fix

| Report item | Correct handling |
|---|---|
| MCP tools missing from host index | Fix host registration/injection; do not create a second stdio server as a workaround |
| safe-delete threshold accumulated per turn | Host policy; avoid manual `Remove-Item` on MCP locks and use `doctor --repair` |
| `PROFILE_ACL_UNSAFE` | Fail closed; do not weaken ACL checks or change ownership automatically |
| `Add-Type` blocked | Expected host policy; no dynamic compile/assembly workaround |
| interactive WinForms test unavailable in headless session | User confirms behavior on the real interactive desktop |

## 5. ask-bridge coexistence

The newer personal Codex workflow is `web-first-ask` + `ask-bridge`. Keep its Chrome Profile and CDP port separate from this legacy MCP. Do not assume port 9223 belongs to chatgpt-web-mcp: this MCP uses the port recorded in its own `browser-state.json`.

This repository remains a maintenance/fallback MCP with four tools and its existing ChatGPT + Gemini two-provider fan-out. New Codex workflows should prefer the CLI-first project to avoid repeated MCP tool-call reasoning during long waits.

## 6. Waiting and Token usage

The 30-second limiter in `createProgressNotifier()` throttles notifications; it is not a prescribed Agent polling interval. The MCP Skill retains the 90-second observation slice because the host transport timeout must be measured before raising it. Do not poll every 30 seconds. The CLI-first `web-first-ask` route is the preferred long-wait path.


## CDP disconnect contract correction (R3.4.5)

For `chromium.connectOverCDP()`, leave Playwright's `_shouldCloseConnectionOnClose` flag `false` and call the public `browser.close()` API. In Playwright 1.62.1 the server-side Chromium `BrowserProcess.close` closes the CDP WebSocket transport (`chromeTransport.closeAndWait`) and does not send a browser-shutdown command to Chrome. Setting the flag to `true` is the `connect()` client-transport path and bypasses the server-side `connectOverCDP` cleanup. The real Chrome verifier checks that the CDP endpoint and marker page survive the detach/reconnect cycle.
